# PicGenTool Python 性能优化设计

## 背景与目标

PicGenTool 当前使用 Python 3.11、PyQt6、Pillow、docxtpl 和 python-docx，将 1～30 张照片裁剪压缩后写入 Word 模板。界面已经通过 `QThread` 避免生成过程阻塞，但图片仍逐张串行处理，且缺少分阶段耗时数据。

本次保留现有 Python 技术栈、用户操作流程、30 个 Word 模板及输出格式，通过测量驱动的方式降低冷启动和批量生成耗时，并保证界面在任务期间可响应。

## 目标

- 建立可重复的 1、10、30 张图片性能基准，记录启动、图片处理、模板渲染和保存耗时。
- 通过受控线程池并行处理图片，保持输入顺序和输出文档顺序一致。
- 优化 JPEG 解码、EXIF 方向处理、裁剪、缩放和编码参数。
- 提供安全的任务取消能力，并保证临时目录被清理。
- 10～30 张典型手机照片的图片处理阶段相对基线降低至少 40%。
- 冷启动时间相对基线降低至少 30%；若 Qt 初始化占据主要耗时，则记录限制而不进行高风险 UI 重写。
- 输出图片尺寸、顺序、方向、文档版式和现有版本保持兼容。

## 非目标

- 不更换 Go、Rust、C++ 或其他语言。
- 不更换 PyQt6，也不重新设计界面。
- 不在本轮取消 30 个 Word 模板或直接重写 DOCX XML。
- 不引入常驻后台服务、数据库或云端处理。
- 不以牺牲明显可见的图片质量换取速度。

## 约束

- 最低 Python 版本保持 3.11。
- 图片上限保持 30 张，目标尺寸保持 6.4 cm × 4.8 cm、240 DPI、JPEG 质量 60。
- 并发默认最多 4 个工作线程，并限制为 `min(4, os.cpu_count() or 1, 图片数量)`。
- JPEG 默认关闭 `optimize`；通过配置保留恢复能力。
- 任何并发失败或取消都必须清理临时文件，且不能留下不完整的目标 DOCX。
- 性能验收在同一台 Windows 设备、同一组样本、至少 3 次运行的中位数上比较。

## 方案选择

### 方案 A：保守参数优化

只增加日志、减少图片复制并调整 JPEG 参数。风险最低，但无法充分利用多核，30 张图片场景的收益可能有限。

### 方案 B：均衡优化（采用）

在参数优化基础上增加受控并发、解码降采样、阶段计时和任务取消。保留现有 UI、服务分层与模板体系，收益和改动风险较均衡。

### 方案 C：深度重构 Word 输出

使用单一模板动态创建布局，或者直接操作 DOCX XML。长期维护潜力较高，但会扩大排版回归范围，在现有性能数据不足时不实施。

## 设计

### 性能观测

新增轻量计时上下文，使用 `time.perf_counter()`，统一记录 `startup`、`image_total`、`image_item`、`layout`、`word_open`、`word_render`、`word_save` 和 `open_output`。日志包含阶段名、毫秒耗时和图片数量，不记录用户图片路径、标题等私人内容。

提供独立基准脚本生成固定尺寸的测试图片并重复执行图片处理。基准结果保存为 JSON，便于优化前后比较；自动化测试只验证结果结构和正确性，不对 CI 中不稳定的绝对耗时设硬断言。

### 图片流水线

`ImageService.prepare_images()` 保持外部接口不变，内部把单图操作提取为 `_prepare_one()`。使用 `ThreadPoolExecutor` 并行处理，各任务写入由原始索引确定的文件名，最终按输入索引返回结果。

单图处理按以下顺序执行：打开图片、对 JPEG 尝试 `draft()` 降采样、应用 `ImageOps.exif_transpose()`、转 RGB、按目标比例居中裁剪、LANCZOS 缩放、以 JPEG 质量 60 且 `optimize=False` 保存。线程只处理自己的 Pillow 对象和输出文件，不共享图像实例。

进度按已完成任务数量计算。任一任务失败时设置取消事件、取消尚未开始的 future、等待已运行任务退出、清理临时目录，并抛出包含原文件名的业务错误。

### 取消机制

生成任务持有 `threading.Event`。图片循环、布局开始前、Word 导出开始前检查事件。用户点击取消后只设置事件，不强制终止线程；当前正在进行的单图编码或 DOCX 保存允许安全完成，然后在下一个检查点退出。

取消属于正常结果，不显示“生成失败”错误框。UI 恢复按钮状态并显示“已取消”。如果取消发生在最终保存前，目标文件不应存在；Word 导出先保存到目标目录的临时文件，成功后使用 `Path.replace()` 原子替换正式文件。

### 启动优化

保留 Pillow、docxtpl 和 python-docx 的延迟导入。为启动入口增加计时，检查是否存在新的顶层重依赖。继续使用 PyInstaller one-dir、`upx=False` 和 `noarchive=True`。只有基准证明图标资源解码或日志初始化占比明显时，才进行针对性改动。

### Word 输出

本轮只拆分计时并采用临时文件原子保存，不改模板渲染行为。如果测量结果显示 `word_render + word_save` 占总耗时超过 50%，单独提出后续 DOCX 架构优化计划。

## 验收标准

- 1、10、30 张图片均能生成与当前模板兼容的 DOCX。
- 并发完成顺序不同也不会改变文档中的图片顺序。
- EXIF 旋转照片方向正确；RGBA、灰度、GIF/BMP 输入仍能转换为 RGB JPEG。
- 损坏图片会给出明确错误，并清理所有临时文件。
- 处理中取消会恢复 UI，不显示失败弹窗，不留下临时目录或不完整 DOCX。
- 自动化测试全部通过；Windows 打包版完成一次 1、10、30 张样本的人工回归。
- 同机三次运行中位数达到图片处理阶段至少 40% 的改善；若冷启动未达到 30%，报告 Qt/PyInstaller 的实测占比和后续建议。
